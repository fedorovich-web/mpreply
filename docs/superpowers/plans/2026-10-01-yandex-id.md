# Yandex ID Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox syntax for tracking. Proposed execution: native in this session, with one final independent review; no task-by-task delegation.

**Goal:** Add Yandex login/registration while preserving cookie-session security, verified email registration, tenant isolation and one trial per owner.

**Architecture:** Backend Authorization Code + PKCE S256 uses one-use database state bound to a host-only browser cookie. An external identity maps a stable Yandex ID to a user. Existing email collisions require local login followed by explicit OAuth linking; they never silently merge accounts.

**Tech Stack:** Existing FastAPI, SQLAlchemy/PostgreSQL, httpx, pytest; Next.js and current auth components, Zod, Vitest, Playwright. No widget SDK or new dependency.

**Spec:** `docs/superpowers/specs/2026-10-01-lava-yandex-integration-design.md`, approved 01.10.2026. Implements its Yandex section; billing has a separate plan. Execute after billing migration 0019 so Alembic remains linear.

## Global Constraints

- Same base/shared-checkout/protected-path constraints as Lava plan. No provider token goes into browser storage, cookie session contents, ordinary logs or permanent identity rows.
- Redirect URI: `https://api.mpreply.ru/api/auth/yandex/callback`, derived from API_BASE_URL. Scopes: login:email and login:info; ignore sex, birthday, phone and avatar.
- Existing email/password registration and cookie names/paths/rotation/auth_version semantics remain unchanged. Local password hash becomes nullable for OAuth-only users; no invented password/email.
- Existing email never auto-links. A link requires an authenticated active user, explicit action and fresh OAuth state tied to user/auth_version. No demo linking.
- UI uses current auth composition/tokens/locales and preserves safe next + marketplace intent. No arbitrary external redirect.
- No actual provider sign-in with user credentials, commit/push/deploy or production enablement during local implementation.

## Review Focus

1. Two callbacks register the same Yandex ID/email concurrently: one identity/user, no orphan or duplicate trial (Task 2).
2. Provider returns a different client_id, missing default_email, or changes email later: reject wrong client; no fabricated account; existing stable identity is not remapped by email (Task 1/2).
3. Password reset/session revocation occurs while linking: stale auth_version cannot attach an identity (Task 2).
4. Multiple browser tabs, canceled consent or replay: another tab's identity is never attached; state stays one-use and errors do not disclose raw codes/tokens (Task 1/3).
5. RU/EN and marketplace intent survive provider errors and local login required for collision, with no open redirect (Task 3).
