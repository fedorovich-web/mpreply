# MPReply: ручная оплата Lava.top и вход через Яндекс ID

Дата: 01.10.2026. Статус: схема подтверждена владельцем продукта 01.10.2026; реализация ещё не начата.

## Основание и границы

Сайт работает на production-доменах. Владелец запросил подключение Lava.top и быструю регистрацию через Яндекс, выбрал ручную оплату без автосписаний и подготовил продукт Lava.top с «Ценой по запросу через API».

Текущая база: `feat/auth-email-resend`, `417add5257b9f5d896ba6d4aca88b39a0d743a19`. Есть cookie-сессии, подтверждение email, RBAC, тарифы, баланс ответов и идемпотентные начисления. Checkout, обработчик платежей и внешние идентичности пока отсутствуют. `.handoff/` и `apps/cms/` не изменяются.

Сохраняются цены из PRODUCT.md: Старт 1 290 ₽ / 300 ответов; Команда 3 490 ₽ / 800; Бизнес 6 990 ₽ / 1 600; годовая оплата со скидкой 20%; существующий каталог дополнительных пакетов; пробные 350 ответов на 14 дней. Корпоративный тариф остаётся через обращение.

## Lava.top

### Подход

Рекомендуется один подготовленный продукт с динамической ценой и прямой HTTP-клиент на существующем httpx. Альтернатива — отдельные офферы для каждой цены — требует повторять каталог в кабинете Lava.top. SDK добавляет зависимость и пока не поддерживает поля возврата покупателя, указанные в официальной документации.

Каждая покупка создаётся через `POST /api/v3/invoice`, в RUB, с явным `periodicity=ONE_TIME`. Рекуррентные списания и подписки Lava.top не создаются. Суммы на стороне MPReply хранятся в копейках; перевод в рубли для запроса выполняется через Decimal.

### Заказ и подтверждение

- Покупку создаёт owner/admin действующей организации. Demo и остальные роли не могут создавать платежи.
- Клиент передаёт тариф и период либо выбранные пакеты и ключ идемпотентности. Цена, количество ответов и итог рассчитываются только сервером.
- До запроса к Lava.top сохраняется заказ: организация, актор, состав, сумма, валюта, ключ, хеш параметров. Повтор с тем же ключом возвращает прежний заказ, изменение параметров запрещено.
- Возвращается только реальный HTTPS paymentUrl от Lava.top. При неопределённом результате POST повторный запрос не создаёт второй платёж автоматически: заказ остаётся на сверке. Для восстановления используется сохранённая корреляция в поддерживаемом `clientUtm.utm_content`; одних UTM-параметров недостаточно для подтверждения оплаты.
- Webhook: `https://api.mpreply.ru/api/billing/lava/webhook`, отдельный секрет в `X-Api-Key`, сравнение за постоянное время. Полученные события фиксируются с уникальным ключом, обработка повторяется безопасно.
- Успех проверяется по контракту Lava.top: ID, конечный оплаченный статус, сумма и валюта из GET invoice, связь с локальным заказом и ID продукта из аутентифицированного webhook. GET invoice возвращает названия продукта/оффера, а не их ID: не использовать названия как доказательство. При обычном создании связь подтверждается сохранённым ответом POST на серверный offerId. При неопределённом результате создания дополнительно проверяется случайная серверная корреляция clientUtm.utm_content и ID продукта из webhook. Email не используется для выбора организации.
- В одной транзакции фиксируются оплаченный заказ, оплаченный период и соответствующее начисление в существующем ReplyCreditService. Повторное или запоздавшее событие не начисляет ответы дважды и не переводит оплаченный заказ в failed.
- Возврат покупателя идёт в кабинет: статус из URL служит только для отображения ожидания проверки. API статуса заказа доступно исключительно участникам соответствующей организации.
- Начальные события в кабинете: `payment.success`, `payment.failed`. Незнакомые аутентифицированные события сохраняются для разбора и подтверждаются без начислений. Автоматические возвраты денег не реализуются. Refund/chargeback без однозначного ID исходного заказа не сопоставляются по email и требуют ручного разбора.

### Предлагаемые правила периодов для одобрения

1. Оплата месяца даёт один календарный месяц; оплата года — 12 месяцев за 80% от суммы 12 месячных платежей. Даты рассчитываются по UTC с корректными границами коротких месяцев.
2. При действующем платном тарифе новый оплаченный период начинается после уже оплаченного. Выбор другого тарифа применяется с начала нового периода; автоматический перерасчёт середины периода отсутствует, прежняя оплата сохраняется.
3. Ответы годового тарифа начисляются помесячно. Планировщик выдаёт уже оплаченные месячные начисления с уникальными ключами и не обращается к платежам для списания денег. После простоя догоняет пропущенные начисления.
4. Дополнительные пакеты начисляются сразу после подтверждения оплаты, не меняют тариф и сохраняются без срока. Для использования оплаченных ответов по-прежнему нужен активный оплаченный период.
5. Источник ручного оплаченного периода хранится отдельно от provider_subscription_id: ID разового платежа не выдаётся за подписку Lava.top.

### Интерфейс

В существующем «Тариф и лимиты»: выбор тарифа/периода, разовая покупка пакета, переход к оплате, состояние ожидания подтверждения, история своих заказов и понятная ошибка. Текущая композиция, токены и ценовой fallback сохраняются. Доступность оплаты определяется конфигурацией сервера и ролью. Публичные цены не меняются.

## Яндекс ID

Рекомендуется серверный Authorization Code + PKCE S256. Альтернатива — виджет мгновенной авторизации с дополнительным скриптом и страницей приёма токена. Серверный вариант подходит существующим cookie-сессиям MPReply и добавляет кнопку «Войти через Яндекс» на входе и регистрации.

- Redirect URI: `https://api.mpreply.ru/api/auth/yandex/callback`. Для этого варианта Suggest Hostname не требуется.
- Минимальные права: `login:email`, `login:info`. Пол, телефон, дата рождения и портрет не сохраняются.
- State одноразовый, ограничен по времени, связан с браузером через Secure HttpOnly cookie. PKCE verifier находится на сервере. При callback состояние атомарно потребляется до обмена кода; повтор, чужой браузер и истёкшее состояние отклоняются.
- Сервер обменивает code на token и получает профиль через HTTPS API Яндекса. Проверяются client_id и устойчивый id. Токен не попадает во frontend, URL возврата, обычные журналы или постоянное хранилище.
- Отдельная таблица идентичностей с уникальностью `(provider, subject)` и `(user, provider)`. Вход выполняется по устойчивому ID, а не по совпадению email.
- Для новой идентичности с валидным default_email создаётся аккаунт без локального пароля. Успешная проверка Яндекс ID является источником подтверждения при регистрации; этот источник фиксируется в аудите. Дальше используются текущие access/refresh-сессии и правила создания рабочего пространства/пробного пакета.
- Уже существующий email не связывается автоматически. Предлагается сначала войти в имеющийся MPReply-аккаунт, затем явно связать Яндекс повторной OAuth-проверкой с привязкой state к текущему пользователю и auth_version.
- При отсутствующем email пользователю предлагается текущая регистрация по email; адрес не выдумывается. Заблокированные аккаунты не допускаются. Локальный вход проверяет nullable password_hash безопасно; восстановление пароля продолжает требовать подтверждённый email.
- Сохраняются locale, безопасный next и intent подключения площадки. Произвольные внешние адреса возврата не принимаются.

## Настройки и ввод ключей

Предлагаемые backend-only переменные: `LAVA_ENABLED`, `LAVA_API_KEY`, `LAVA_OFFER_ID`, `LAVA_PRODUCT_ID`, `LAVA_WEBHOOK_SECRET`, `YANDEX_OAUTH_ENABLED`, `YANDEX_OAUTH_CLIENT_ID`, `YANDEX_OAUTH_CLIENT_SECRET`. Callback выводится из API_BASE_URL. Значения секретов владелец вводит непосредственно в Dokploy; в чат и Git они не передаются.

При выключенной интеграции старые регистрация и кабинет продолжают работать. При включённой интеграции неполная конфигурация блокирует её запуск, а не выдаёт фиктивный успех. Флаги включаются только после миграций, конфигурации кабинетов и проверки контрактов.

## Проверки и запуск

Регрессии до реализации: подмена суммы/организации/роли; повторы и конкуренция заказа/webhook; таймаут создания; неверный секрет; порядок success/failed; годовые месячные начисления; границы и перенос периодов; просроченный доступ; чужой/повторный OAuth state; PKCE; коллизия email; nullable пароль; заблокированный пользователь; повторная пробная выдача; безопасный redirect.

Внешние платежи и вход Яндекса в автоматических тестах заменяются контрактными HTTP-ответами. PostgreSQL проверяет миграции, ограничения и конкуренцию. Затем обязательные backend/frontend gates и браузерная проверка интерфейсов. Visual сохраняет честный отдельный результат, снимки не обновляются ради зелёного статуса.

Реальный OAuth-вход выполняет владелец. Реальная оплата требует отдельного согласования суммы и проверки кабинета Lava.top. Коммит, push и новый production Deploy согласуются по подготовленному diff и результатам; прежнее разрешение относилось к исправлению регистрации.
