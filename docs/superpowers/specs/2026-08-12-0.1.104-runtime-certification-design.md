# MPReply 0.1.104 CI and marketplace runtime certification design

Date: 2026-08-12
Release target: `0.1.104`
Feature branch: `codex/0.1.104-backend`
Baseline before this document: `c24d9d8e08f930e695871ef5adec746c8def8d67`
Status: approved design for implementation planning

## 1. Purpose

Turn the completed marketplace backend slices into a release-candidate-quality, evidence-backed integration without claiming production readiness that has not been verified.

This batch has two outcomes:

1. make the repository Quality Gate and production container build run for the current `work/**` integration flow;
2. add one consistent, fail-closed runtime certification surface for Wildberries, Yandex Market, Ozon, and Avito.

The provider certification order is fixed:

1. Wildberries;
2. Yandex Market;
3. Ozon;
4. Avito.

Wildberries remains the primary product execution path. The other providers must not be described as production sending paths until their runtime evidence has been reviewed.

## 2. Verified baseline

At the design baseline:

- pull request `#11` targets `work/0.1.104-yandex-foundation`;
- `.github/workflows/quality-gate.yml` listens only to pull requests targeting `main` or `develop`, so the current pull request has no remote Quality Gate run;
- the Quality Gate already has backend, frontend, and production-container jobs;
- its production-container job builds API, worker, and web images but omits `apps/scheduler/Dockerfile`;
- `scripts/container-gate.ps1` validates and starts the local Compose stack, checks API and web readiness, and writes `.handoff/container-gate-result.json`;
- the Docker Desktop Linux engine was unavailable during the last local container verification attempt;
- only Yandex Market currently has a dedicated runtime probe and PowerShell wrapper;
- `.handoff/` is ignored by Git;
- marketplace adapters use HTTPX without an explicitly configured retry transport in production construction;
- existing tests use transport injection to exercise HTTP behavior without live provider calls.

These statements describe repository state at the baseline SHA. They are not runtime provider evidence.

## 3. Scope

### 3.1 Included

- enable the existing Quality Gate for pull requests targeting `work/**`;
- cancel superseded runs for the same branch or pull request;
- build all four production images: API, worker, scheduler, and web;
- preserve a separate local container runtime gate;
- extract a provider-neutral runtime-probe core from the existing Yandex implementation without changing its approved behavior;
- add provider-specific probes and PowerShell wrappers for Wildberries, Ozon, and Avito;
- keep Yandex Market compatible with its existing read and write modes;
- add provider-specific read-only and explicitly armed write certification modes;
- create sanitized atomic evidence in `.handoff/`;
- cover the new code with focused unit tests using synthetic HTTP transports;
- perform one grouped final repository gate after implementation changes settle.

### 3.2 Excluded

This batch does not:

- implement integration UI for Ozon or Avito;
- change public-site capability claims;
- add another marketplace provider;
- deploy, merge, tag, publish images, or bump the version;
- put marketplace credentials in GitHub Actions;
- call live marketplace APIs from tests or CI;
- run live write probes without separate operator authorization and exact targets;
- redesign the reply, scheduler, credential, or marketplace domain models;
- weaken existing checks to obtain a green result;
- perform another write to protected Yandex Question ID `27265525`.

The product integration UI is a later stage after runtime certification. Its current provider-state labels must not be changed based only on unit tests.

## 4. Approaches considered

### 4.1 Independent probe implementations

Each provider could receive a standalone script copied from the Yandex probe. This minimizes the first edit but duplicates redaction, evidence writing, mode validation, page budgets, and write guards. Safety behavior would drift between providers. This approach is rejected.

### 4.2 One generic probe containing all provider logic

A single large command could branch on the provider. It would centralize entry points but mix unrelated provider identifiers, streams, preflight rules, and write semantics. A change for Avito chat behavior could affect review/question providers. This approach is rejected.

### 4.3 Shared safety core with thin provider modules

The selected approach extracts only invariant mechanics into a common core and keeps provider operations in dedicated modules. This provides one evidence and write-safety contract without pretending the provider APIs are identical.

## 5. Runtime-probe architecture

### 5.1 Shared core responsibilities

The shared runtime-probe core owns:

- normalized modes and statuses;
- validation of required configuration;
- maximum page budgets;
- credential and identifier fingerprinting/masking;
- sanitized step recording;
- explicit write arming and exact confirmation checks;
- fail-closed ambiguity classification;
- atomic JSON evidence creation;
- evidence self-inspection for forbidden raw values;
- stable exit-code mapping.

The core does not know provider endpoints, response DTOs, scopes, pagination tokens, or how to determine whether a reply already exists.

### 5.2 Provider modules

Provider behavior remains in thin modules:

- `wildberries_runtime_probe.py`;
- `yandex_market_runtime_probe.py`;
- `ozon_runtime_probe.py`;
- `avito_runtime_probe.py`.

Each module supplies:

- credential and account configuration;
- supported modes;
- bounded read operations;
- provider-specific preflight and postflight reconciliation;
- provider-specific exact write confirmation phrase;
- target validation;
- mapping from adapter results to sanitized evidence steps.

The existing Yandex probe is migrated incrementally. Its observable CLI, environment, read behavior, confirmation rule, page cap, and evidence guarantees remain covered while common mechanics are extracted.

### 5.3 PowerShell wrappers

Each provider receives a separate wrapper. A wrapper:

1. accepts only non-secret mode and budget options as normal parameters;
2. obtains credentials through `SecureString` or an already populated environment variable;
3. exports secrets only to the child process environment;
4. never puts secrets or reply text in command-line arguments;
5. invokes the corresponding Python module;
6. verifies that evidence was written;
7. scans the evidence for raw credentials, full identifiers, and the write text;
8. clears process-local secret environment values in `finally`.

The wrappers write:

- `.handoff/wildberries-runtime-verification.json`;
- `.handoff/yandex-market-runtime-verification.json`;
- `.handoff/ozon-runtime-verification.json`;
- `.handoff/avito-runtime-verification.json`.

## 6. Runtime modes and provider behavior

### 6.1 Common read-only contract

Read-only mode always runs credential validation first. It then performs only bounded provider reads, normalization, and pagination checks. It does not mutate local application data or provider state.

No automatic retry is added. A transient error produces a completed evidence file and a non-success status. A later attempt is an explicit operator action.

### 6.2 Wildberries

Read-only mode verifies credentials and bounded review/question reads through the production adapter, including normalization and cursor behavior.

Write modes are:

- `write-review`;
- `write-question`.

They use the adapter's exact-item lookup/reconciliation before a single send attempt and reconcile again afterward.

### 6.3 Yandex Market

The existing modes remain:

- `read-only`;
- `write-review`;
- `write-question`.

The existing credential validation, bounded review/question pages, preflight, send, postflight, and evidence behavior are preserved.

Question ID `27265525` is permanently read-only. The shared write guard and Yandex provider module both reject it before any provider write method can run.

### 6.4 Ozon

Read-only mode verifies API key and Client ID together, validates exact roles/scopes, and reads only streams authorized by the returned capability set.

Write modes are:

- `write-review`;
- `write-question`.

Each uses its provider-specific existing-reply check before a single send attempt and performs reconciliation afterward.

### 6.5 Avito

Read-only mode validates credentials and performs bounded chat and message reads.

`mark_chat_read` is a provider mutation and must never run in read-only mode.

Write modes are intentionally separate:

- `write-chat-message`;
- `write-mark-read`.

Chat-message preflight searches for an outbound message after the selected inbound message. Send confirmation uses the returned outbound message contract and a bounded postflight read. Mark-read uses its own target and confirmation phrase and cannot be armed accidentally by the chat-message mode.

## 7. Write safety contract

A write mode is valid only when all of these are present:

- exact provider-specific confirmation phrase;
- exact operation-specific target identifier;
- valid provider account/seller identifier when required;
- reply text supplied through protected input for message/reply modes;
- successful credentials and scope validation;
- successful preflight proving no existing reply for that target.

The execution sequence is fixed:

1. validate configuration without network access;
2. validate credentials and required scopes;
3. read and validate the target;
4. run provider-specific existing-reply preflight;
5. record an armed write intent in memory;
6. make exactly one provider write call;
7. perform bounded provider-specific reconciliation;
8. atomically write final evidence.

The probe never uses the broker, scheduler, or application retry state machine. It never retries a provider write.

Once POST or PATCH begins, the following outcomes are classified as `AMBIGUOUS` unless provider reconciliation proves the result:

- timeout;
- connection/request error;
- HTTP 429;
- HTTP 5xx;
- malformed success response;
- contradictory provider response;
- postflight failure or page-budget exhaustion.

An ambiguous result stops the probe and instructs the operator to inspect the provider cabinet. It does not offer or schedule a resend.

## 8. Evidence contract

### 8.1 Statuses

Only these final statuses are allowed:

- `PASS`: the requested read or write verification is confirmed;
- `FAIL`: a definite non-ambiguous failure occurred before a provider write;
- `BLOCKED`: required access, scope, configuration, Docker capability, or operator input is unavailable;
- `AMBIGUOUS`: a provider mutation may have occurred but cannot be confirmed safely.

### 8.2 Required fields

The versioned evidence object contains:

- `schema_version`;
- `provider`;
- `mode`;
- `status`;
- `started_at` and `finished_at` in UTC;
- repository Git SHA and application version;
- SHA-256 credential fingerprint;
- masked account/seller identifier;
- configured and consumed page budget;
- sanitized operation steps;
- normalized adapter error code and bounded `retry_after_seconds` when supplied;
- read item counts without content;
- for writes: target fingerprint, preflight outcome, `write_attempted`, and postflight confirmation state.

### 8.3 Forbidden fields and values

Evidence, stdout, and exception text must not contain:

- credentials or authorization headers;
- full account, seller, chat, message, review, or question identifiers;
- reply/message text;
- customer messages, reviews, or questions;
- raw HTTP request/response bodies;
- personal data;
- unfiltered provider exception representations.

Safe adapter error codes may be stored. Error messages are selected from local constants rather than copied from provider responses.

### 8.4 Atomicity

Evidence is written to a temporary file in the target directory, flushed, and atomically replaced into its final path. A failed or interrupted run must not leave a partially valid final JSON file.

The wrapper performs a second defensive scan for the exact secret values it received. Detection fails the command and prevents a passing result.

## 9. GitHub Quality Gate design

### 9.1 Trigger correction

The workflow first lands through a minimal prerequisite change in the current target branch. The pull-request base filter becomes:

- `main`;
- `develop`;
- `work/**`.

GitHub evaluates `pull_request.branches` against the target branch. The current pull request therefore cannot be relied on to self-enable a workflow whose base filter excludes its target. After the prerequisite change reaches the target branch, pull request `#11` is synchronized or reopened to create a run for its current SHA.

`workflow_dispatch` is not used as the primary correction because GitHub only receives that trigger when the workflow file is on the default branch.

### 9.2 Concurrency

The workflow uses a repository/workflow/ref concurrency group and cancels an older in-progress run when a newer commit arrives for the same pull request or branch.

### 9.3 Secret boundary

The Quality Gate remains secret-free. Its placeholder environment exists only for Compose interpolation and image build validation. No provider probe is imported as an automatic live test, and no marketplace credential is configured as a repository or environment secret for this workflow.

## 10. Container gates

### 10.1 Remote production image gate

The existing container job remains dependent on successful backend and frontend jobs. It:

1. validates production Compose with explicit CI placeholders;
2. builds the API image;
3. builds the worker image;
4. builds the scheduler image;
5. builds the web image.

It does not push images, start production services, run migrations against an external database, or call marketplace APIs.

The duplicated Compose-validation step is made unambiguous so each retained validation has a distinct purpose and name. If the `.env.ci` validation has no separate contract, it is removed rather than duplicated.

### 10.2 Local runtime container gate

`scripts/container-gate.ps1` remains the local integration gate. It validates local Compose, builds and starts the stack, waits for services, checks API and web readiness, records evidence, and shuts the stack down unless explicitly asked to keep it running.

The gate is run once after implementation when the Docker Desktop Linux engine is available. If the daemon remains unavailable, the result is `BLOCKED` with the exact daemon error; it is not reported as a pass and unchanged test suites are not rerun to compensate.

## 11. Testing strategy

Implementation follows focused test-driven development:

1. add one grouped RED test set for the new behavior;
2. implement the shared core and provider modules in bounded tasks;
3. run one grouped GREEN set after the related implementation settles;
4. run lint and strict typing for touched backend files;
5. run workflow/static validation for changed scripts and YAML;
6. run one final full affected-repository gate;
7. run the local container gate once if Docker is available.

Tests use synthetic identifiers and `httpx.MockTransport`. Runtime probe modules are never executed against live providers by pytest.

Required coverage includes:

- mode and required-field validation;
- exact confirmation phrases;
- protected Yandex identifier rejection;
- credential and identifier redaction;
- atomic evidence replacement;
- page-budget boundaries and pagination cycles;
- provider-specific preflight and postflight behavior;
- no write after failed preflight;
- exactly one write call after successful preflight;
- timeout, network error, 429, 5xx, malformed success, and failed reconciliation after write start becoming `AMBIGUOUS`;
- no automatic retry for read or write operations;
- Avito read-only mode never calling `mark_chat_read`;
- production workflow building the scheduler image;
- `work/**` pull-request targets matching the Quality Gate.

Existing Yandex runtime-probe tests are retained as compatibility tests during extraction.

## 12. Certification run order

After code and container gates are green, provider certification proceeds serially.

For each provider:

1. operator supplies credentials locally or in an approved secure staging environment;
2. run read-only mode once;
3. inspect the sanitized evidence and provider cabinet;
4. resolve any definite contract defect before continuing;
5. obtain separate authorization and exact disposable target for a write, if write certification is required;
6. run the single write probe;
7. inspect postflight evidence and the provider cabinet;
8. record the provider as verified, blocked, failed, or ambiguous;
9. only then continue to the next provider.

A failure for one provider does not silently downgrade the gate or produce a capability claim. It stops that provider's certification and leaves later providers unverified until an explicit decision is made to continue read-only checks.

## 13. Acceptance criteria

The implementation stage is complete only when:

1. the approved design has a separate implementation plan;
2. the Quality Gate triggers for a pull request targeting `work/**`;
3. one remote Quality Gate run is green for the current pull-request SHA;
4. backend and frontend jobs retain their existing required checks;
5. production Compose validates;
6. API, worker, scheduler, and web production images build;
7. the common probe core and all four provider modules pass focused tests;
8. strict backend typing and Ruff pass for touched scope;
9. evidence redaction tests prove raw credentials, identifiers, content, and reply text are absent;
10. every write path performs at most one provider mutation;
11. ambiguous post-write outcomes cannot enter a retry path;
12. the local container gate is either passed once or truthfully recorded as blocked by the Docker daemon;
13. no live provider call has been made without separate operator authorization;
14. no version bump, deploy, image push, merge, or public capability claim is included.

Runtime certification itself is complete only when each provider's actual evidence has been separately reviewed. Until then, its runtime state is `unverified` or the exact observed non-pass status.

## 14. Implementation planning boundary

The implementation plan will split work into reviewable commits in this order:

1. Quality Gate trigger/concurrency and scheduler image build;
2. shared runtime evidence and safety core;
3. Yandex compatibility extraction;
4. Wildberries probe and wrapper;
5. Ozon probe and wrapper;
6. Avito probe and wrapper;
7. grouped verification, remote CI evidence, and local container gate;
8. provider-by-provider runtime runbook, without executing live calls automatically.

No implementation work starts until this design document is committed and the implementation plan is written and reviewed.
